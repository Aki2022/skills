# Design Check Routing

デザイン検査の**ルーター**。検査そのものは持たない。持つのは 3 つだけ:
**対象の判定・カバレッジ表・実行順序**。

## なぜルーターが要るか

導入済み skill は 59 個あり、デザイン検査に関わるものだけで 9 個ある。
個別名を覚えるのは現実的でなく、文脈発火（description の文字列マッチ）は
発火しなかった skill が**沈黙する** — 呼ばれなかったことは誰にも見えない。

このルーターは逆の契約を結ぶ: **実行しなかった検査を、理由つきで必ず報告する。**
漏れをゼロにはできないが、漏れを**見える**ようにはできる。

## 手順

### 1. 対象を判定する

| 対象          | 判定の手がかり                                      |
| ------------- | --------------------------------------------------- |
| LP            | 広告流入前提・CV（ボタン/フォーム）がある単一ページ |
| プロダクト UI | ログイン後の画面・ダッシュボード・操作が主目的      |
| 資料          | スライド・PDF・レポート・HTML 文書                  |

迷ったら聞かずに「LP として扱う」と宣言して進める（検査が最も厚いため）。

### 2. カバレッジ表に沿って連鎖する

**この表がこの skill の本体。** 空欄は「担当が存在しない」ことの明示であり、
検査を実行できない観点は報告にもそのまま**欠落**として書く。

| 観点                             | LP                                            | プロダクト UI                                                        | 資料                                                       |
| -------------------------------- | --------------------------------------------- | -------------------------------------------------------------------- | ---------------------------------------------------------- |
| 審美・レイアウト実測（決定論）   | `origin-lp-review` の `measure_lp.mjs`        | 同スクリプト流用可。ただし `fold-cta` 等 LP 前提の検査は解釈を添える | `origin-design-runtime` の validator（自己点検が主・弱い） |
| マーケ定性（独立レビュアー採点） | `origin-lp-review` の rubric                  | **欠落**                                                             | **欠落**                                                   |
| 広告審査・法務・SEO・計測        | `origin-website-audit`                        | `origin-website-audit`（該当節のみ）                                 | 対象外                                                     |
| UI ガイドライン準拠              | `web-design-guidelines`                       | `web-design-guidelines`                                              | 対象外                                                     |
| アクセシビリティ修正             | `fixing-accessibility`                        | `fixing-accessibility`                                               | **欠落**（validator の自己点検のみ）                       |
| 表示性能（Core Web Vitals）      | `web-perf`                                    | `web-perf`                                                           | 対象外                                                     |
| AI 生成様式の検出                | `baseline-ui`                                 | `baseline-ui`                                                        | **欠落**                                                   |
| ブランド一貫性                   | `origin-design-runtime` validator（自己点検） | 同左                                                                 | 同左                                                       |

補足:

- `origin-lp-review` は LP の「審美実測 + マーケ定性 + ゲート」を 1 つで持つ。
  LP のときは個別に並べず、まず `origin-lp-review` を呼ぶ。
- 重複 skill が既知: `baseline-ui` と `source-command-baseline-ui`、
  `fixing-accessibility` と `source-command-fixing-accessibility`（内容に差分あり）。
  ルーターは **`source-command-` 無し側**を使う。統合は `origin-skill-commonize` の管轄。

### 3. 実行順序 — 決定論が緑になるまで非決定論へ進まない

`origin-lp-review` のゲート原則をルーター全体に適用する:

```
決定論（実測・機械検査） → 失格が残る間は直して再実測 → 非決定論（独立レビュアー・自己点検） → 委譲（audit）
```

理由: 表示が壊れたページを人（AI）が評価すると、出てくるのは表示不良の指摘だけで、
本来見たかった評価が汚染される。非決定論の検査は高い（レビュアー 1 名で数万トークン）。

コピーや構造を直したら、必ず決定論からやり直す。

### 4. 報告の契約 — 沈黙させない

最終報告には必ず 3 区分を書く:

1. **実行した検査**とその結果（失格 / 警告 / スコア）
2. **スキップした検査**と理由（対象外 / 前段の失格で未到達 / ユーザー指示）
3. **欠落**（カバレッジ表の空欄に該当し、そもそも担当 skill が無い観点）

「実行しなかったものは書かない」を許すと、このルーターの存在意義が消える。

## カバレッジ表の保守

- 新しい検査 skill を導入・作成したら、この表に行か列を足す。
  表に載っていない skill はルーターから呼ばれず、再び沈黙に戻る。
- 空欄を埋めた（欠落を解消した）ときは、その skill 名で空欄を置き換える。
- 表の変更はこのファイルの編集で完結する（`origin-skill-commonize` の
  symlink 規約に従い、どの別名から編集しても正典が更新される）。

# 呼び出し規約（工場から）と単発利用（人間から）

読者は2種類 — 将来この窓口を呼ぶ工場 skill の実装者と、単発でイラスト生成を頼まれた人。
どちらも「値をどこから取るか」で迷いやすいので、その出所をまず固定する。

## A. 工場から呼ぶ（例: ある工場 skill の「アセット生成工程」からイラストを N 枚要求する場合）

1. 工場が10フィールドの値を確定する。本 skill は値を持たないので、呼び出し側が埋める。
   - **ブランド軸**（`Style` / `House structure` / `Color palette` / `Style references`）は、
     工場が参照する**ブランド倉庫**（そのプロダクト・サービスの意匠を持つ正典）から**逐語**で
     取る。ここで言い換えたり要約したりしない — 言い換えるとセット内で見た目が割れる。
   - **媒体軸**（`Constraints` / `Avoid`）は、工場が持つ**その媒体の適合規約**（アスペクト比・
     余白・テキスト量の上限など、出力先の媒体ごとに異なる制約）から取る。
   - 残りのフィールド（`Use case` / `Asset type` / `Composition` / `Content`）は、工場がその
     工程の目的（今回何のために何枚要るか）から都度組み立てる。
2. 10キーを持つ `fields.json` を書き出す。キー名は器のラベルと一字一句一致させる
   （下記 B の実例を参照）。
3. アンカー画像を使う場合は、ブランド倉庫にある**人間承認済みの実物**画像のパスを集めて
   `--anchor` に渡す。渡すと `Style references` は窓口側で edit-mode 指示に上書きされるので、
   `fields.json` 側の `"Style references"` は空文字でよい。生成物をアンカーにしない
   （劣化が累積する）。
4. 欲しい枚数だけ `--out` にパスを並べる。出力パスの数がそのまま要求枚数になる。
5. 実行する。

   ```bash
   python3 origin-image-gen/scripts/image_gen.py \
     --fields fields.json \
     --out out/asset_01.png out/asset_02.png out/asset_03.png \
     --anchor brand/anchors/sample_01.png \
     --workdir process/imagegen
   ```

6. exit code を見る（下記の表）。`0` 以外なら成果物を使わず、表の分岐に従う。
7. `0` なら `--out` に書いたパスのリストをそのまま成果物として受け取り、工程を進める。
   同じディレクトリに残る `prompt.txt` / `run.log` は障害調査用の記録なので消さずに残す。

## B. 単発利用の最小手順（例:「イラストを3枚作って」と直接頼まれた場合）

1. 依頼文から `Use case` / `Asset type` / `Content` を都度書く。ブランド軸・媒体軸の値が
   依頼の中で与えられていなければ汎用値で埋める。**特定企業の実際のブランド値を推測して
   書かない** — 汎用の見た目でよいので、依頼された枚数と内容を優先する。
2. `fields.json` を作る（実例。値はすべて汎用のダミーで、特定企業のものではない）。

   ```json
   {
     "Use case": "infographic-diagram",
     "Asset type": "illustration, 4:3",
     "Style references": "",
     "Style": "flat vector illustration, soft rounded shapes, thin 2px outline, minimal shading",
     "House structure": "one central icon inside a circular frame, supporting elements arranged symmetrically around it, no background scenery",
     "Composition": "a single explanatory device such as a simple arrow flow or a grouped icon cluster — choose whichever best fits the content below",
     "Content": "「作業を自動化する」という概念を表す1枚",
     "Color palette": "#2E6F6B（深い青緑）と #F2E9DC（温かみのあるオフホワイト）の2色を基調とする",
     "Constraints": "文字は入れない。上下左右5%の余白を確保する。指定のアスペクト比を守る",
     "Avoid": "写実的な人物描写、ロゴや商標の混入、実在の地名・建物"
   }
   ```

3. 実行する。

   ```bash
   python3 origin-image-gen/scripts/image_gen.py \
     --fields fields.json \
     --out out/illustration_01.png out/illustration_02.png out/illustration_03.png
   ```

4. exit `0` なら3枚のパスをそのまま提示する。exit ≠0 なら下記の表に従う
   （直して再実行か、不合格として人間に報告するか）。

## 渡すもの／渡さないものの表

| 渡す                                            | 渡さない                                                                         |
| ----------------------------------------------- | -------------------------------------------------------------------------------- |
| `fields.json`（10キー全てを埋めたもの）         | 設計意図・仕様書そのもの                                                         |
| `--out` の出力先パス（欲しい枚数分）            | 生成物の配置・命名規約の決定（呼び出し側が先に決めてから `--out` に反映する）    |
| `--anchor` の人間承認済み実物画像のパス（任意） | 生成物から作ったアンカー（劣化が累積するため不可）                               |
| `--workdir` / `--dry-run` 等の実行オプション    | シート内部の環境変数（窓口が内部だけで切り替えるので呼び出し側が渡す必要はない） |

## exit code ごとの分岐

| exit | 意味                                                                                            | 呼び出し側の行動                                                                                                                                  |
| ---- | ----------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| `0`  | 要求枚数が揃って回収できた                                                                      | `--out` のパスをそのまま成果物として使う                                                                                                          |
| `1`  | 生成数が出力名数に足りない／回収失敗／実行そのものの失敗。**判定は行われた上での不合格**        | 成果物を使わない。同じディレクトリの `run.log` で原因を確認し、フィールド値やアンカーを見直して再実行するか、原因が解消できないなら人間に報告する |
| `2`  | 入力不備（`fields.json` のキー欠落・JSON 不正・`--out` が0件 等）。**判定はまだ行われていない** | `fields.json` や引数の形を直してから再実行する。直せば同じ依頼で再試行してよい                                                                    |

`1` と `2` の違いはここが要点: `2` は器の形が崩れていて生成そのものがまだ始まっていない
（直せば済む、失敗ではない）。`1` は生成は動いたが結果を受け取れる形にならなかった
（不合格として扱う。フィールドの中身か実行環境を疑う）。

## やってはいけないこと（再掲。詳細は SKILL.md）

- 不足枚数を他の手段（過去の生成物の使い回し・別ツールでの穴埋め）で埋めない。停止して報告する。
- `.stale` に退避された旧ファイルを成果物として使わない。
- プロンプト文中の「Xとして保存して」という指示を保存の証拠にしない。実際に `--out` のパスへ
  回収されたか（exit code と実ファイルの存在）だけを見る。

## `origin-output-eval` との接続

生成した画像の**品質評価**（合否判定・再生成の要否の判断）は本 skill の仕事ではなく、
`origin-output-eval` が持つ。工程の順序は一行で言える:
本 skill で生成 → `origin-output-eval` で評価 → 不合格ならフィールド値を直して本 skill を再度呼ぶ。

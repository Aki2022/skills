# LP Review

LP の評価に必要な観点は 4 つある。**性質が違うので、道具も分ける。**

| 観点                      | 決定論か   | 誰が判定するか                               | このスキルでの扱い           |
| ------------------------- | ---------- | -------------------------------------------- | ---------------------------- |
| 審美・レイアウト          | **できる** | `scripts/measure_lp.mjs`                     | 所有する（実測）             |
| マーケティング定性        | できない   | 独立レビュアー（作っていないエージェント）   | 所有する（項目別スコア）     |
| 広告審査・法務・SEO・計測 | 部分的     | `origin-website-audit`                       | **委譲する**（再実装しない） |
| コードの正しさ            | できる     | リポジトリのテスト / `web-design-guidelines` | 委譲する                     |

## 中心にある問題

**審美とマーケ定性は自己点検になりやすく、作った本人が緑にしてしまう。**

実例（2026-08-11、このスキルを作る動機になった事故）: LP のヒーロー画像を
「図版として見せる」形に直したエージェントが、ダークモードだけを目視して完了と報告した。
既存の validator は 15/15 PASS。しかしライトモードでは見出しが地と同系色になり、
コントラスト 1.1 で**ほぼ読めない状態**だった。存在チェック（`lang` があるか、
`alt` があるか）は通るが、**見えているかは誰も見ていなかった**。

この 1 件が方針を決めている:

- **審美は実測に落として決定論にする。** 人の（AI の）目に判定を委ねない。
- **決定論にできない部分は、作っていない者が採点する。** 自己点検にしない。
- **測れなかったものを緑にしない。** 未検証は未検証として出す。

## 手順

### 1. 対象と文脈を確定する

- 対象 URL（本番 / ステージング / ローカル）。ローカルなら先にサーバを起こす。
- コンバージョンの定義（このリポジトリなら LINE 友だち追加）。
- 対象読者。リポジトリに persona / PRD / 分析結果があれば読む。
  **無ければ調べに行かない** — ルーブリックの一般アンカーで採点する（後述）。

### 2. 審美・レイアウトを実測する

```bash
node <skill>/scripts/measure_lp.mjs <url> --viewports 375,1280 --schemes dark,light --json /tmp/lp.json
```

playwright が要る。解決できない場合はエラーで止まる（黙って skip しない）。

出力は 2 レーンに分かれる。

- **失格（exit 1）** — 決定論的に確定した欠陥。放置しない。
- **警告（exit には影響しない）** — 近似値・環境差があり、目視で確かめる項目。
  失格に混ぜない。混ぜると「常に赤い検査」になり本物が埋もれる。

検査項目と閾値の根拠は `references/aesthetic-thresholds.md`。
**閾値を緩めるときは必ずそこに理由を残す。** 黙って緩めると検査が意味を失う。

### 2.5. ゲート — 決定論が緑になるまで、非決定論へ進まない

**失格が 1 件でも残っているうちは、独立レビュアーを走らせない。**

理由は費用と信頼性の両方にある。レビュアーは 1 人あたり数万トークンを使う一方、
表示が壊れたページを採点しても出てくるのは表示不良の指摘だけで、
**本来見たかったコピーと訴求の評価は汚染される**。

2026-08-11 に実際にこれで無駄を出した。ライトモードで見出しが読めない状態のまま
3 人を走らせ、全員が同じ表示不良を最重要欠陥として報告した。採点 10 項目のうち
2 項目が使い物にならず、1 人は再実行になった。ゲートがあれば起きなかった。

**再入も同じ順序で行う。** レビュアーの指摘を受けてコピーや構造を直したら、
次は必ず**実測からやり直す**。文言の差し替えは行長・折り返し・
ファーストビューの収まりを壊すため、直した結果が決定論の検査を割ることがある。

```
実測 → 失格あり → 直す → 実測 → …（緑になるまで）→ 採点 → 直す → 実測 → …
```

例外は 1 つだけ。**その失格が「採点対象の面に影響しない」と実測で言える場合**
（例: フッターのタップ領域のみが失格で、採点は本文の訴求が対象）。
この例外を使ったときは、どの失格を残したまま採点したかを報告に明記する。

### 3. マーケティング定性を独立レビュアーで採点する

`references/marketing-rubric.md` の 10 項目を、**そのページを作っていない**
エージェントに採点させる。作った本人にはやらせない。

- 3 人のレビュアーを**別々の観点**（初見の当事者 / 懐疑的な非当事者 / 競合比較）で走らせる
- 各項目 0〜4 点。アンカー文が書いてあるので、点をつける根拠は文章でなく**アンカーへの一致**で決める
- 3 人の**中央値**を採る。平均にしない（1 人の極端値に引かれる）
- 2 点以下の項目は、**具体的な書き換え案**を必ず添えさせる

### 4. コンプライアンス・SEO・計測を委譲する

`origin-website-audit` を使う。ここで再実装しない。
このリポジトリのように広告ポリシーの禁止語ゲートがある場合は、その正典
（テストファイル・仕様）を audit の文脈として渡す。

### 5. 報告する

- **失格**（決定論）→ 修正必須。証拠は数値。
- **低スコア項目**（定性）→ 書き換え案つきで提示。判断は人間。
- **警告・未検証**→ 「見ていない範囲」として明記する。省略した検査も書く。

## やってはいけないこと

- 作ったエージェントに定性スコアをつけさせる（自己点検の温床）
- 実測できる項目を「目視で確認しました」で済ませる
- 閾値を、目の前のページが通るように黙って調整する
- 警告を失格に混ぜる／失格を警告に降格して緑に見せる
- 対象読者の根拠を毎回ウェブで調べ直す（現実的でない。ルーブリックで扱う）

## 既知の限界（v1）

正直に書いておく。ここを知らずに使うと誤読する。

- **画像の上の文字のコントラスト**は近似（背景の代表色を画素の最頻値で推定）。
  狭い箱では文字自身を拾う。現状は**警告**で、目視確認が要る。
- **`image-sunk`（絵が地に沈んでいる）の閾値は未校正。** 意図的に暗い写真で
  誤検知する。サンプルが増えるまで警告に留めている。
- **和文の分かち書きは検出できていない。** 複合語が行末で割れる
  （「ふりかえり」→「ふりか／えり」）型は、現状どの検査にも掛からない。
- **headless の webfont 読み込みは実ブラウザと揺れる。** CJK webfont は
  unicode-range で ~120 分割されるため、`document.fonts.check()` は当てにならない。
  「その family の FontFace が 1 つも loaded でない」場合だけを警告している。
- 第三者ホスト（フォント CDN 等）の 4xx は失格にしない。自ホストの資源だけが失格。

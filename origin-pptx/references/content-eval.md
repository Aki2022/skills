# content-eval — コンテンツ評価ループ

**base.md／outline.md／画像（mockup・preview）の各段階で、subagent による読者評価を
基準点まで反復する工程**。旧「②.5 ペルソナレビュー」文書（②.5 限定）を一般化して置き換えた
（2026-08-31・spec: skills リポ `docs/specs/pptx-content-eval-loop.md`。
20260831_nissay デッキで v8→v14 を駆動した実運用の正典化）。

**本工程（AI評価・計画承認制）と ④.5（人間の画像確認・必須）は別物**: 本工程は AI による
品質評価で、人間ゲート（①共同確定・②承認・④.5）の代替にならない。**AI 審査の合格を
人間確定の代理にしない**——2026-08-31 に AI 審査6回合格の直後、人間の初見レビューで
本編が全面差し戻しになりモックアップ20枚を廃棄した実測がある。

## 読者評価と一致検査は別の活動（混ぜない）

| 活動                          | 目的                           | 評価者                      | 入力                                                  |
| ----------------------------- | ------------------------------ | --------------------------- | ----------------------------------------------------- |
| **読者評価**（本書）          | 読み手に効くか・一読で分かるか | 審査員・初見読者            | **その段階で読み手が実際に受け取る成果物・それ単独**  |
| **一致検査**（pipeline.md ④） | 仕様どおりに施工されたか       | VLM構図比較・数値監査・検分 | 仕様（outline・mockup・base.md 該当節）との照合が本務 |

**読者評価にサイド情報を渡さない。** 画像段階の審査員・初見読者に outline.md 等を併給すると、
実際の読み手が持たない情報で評価が現実から歪む（2026-08-31 人間指摘）。一致検査は逆に
仕様を読むのが仕事であり、読者評価の代替にはならない。

### 段階マップ（評価対象＝対象単独）

| 段階                      | 読者評価の入力               | 補足                                                                                                                                            |
| ------------------------- | ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| base.md（骨子）           | base.md のみ                 | Layer A 中心。Evidence Ledger は骨子の一部として含めてよい                                                                                      |
| outline.md                | outline.md のみ              | **outline は本文・構図メモ・出典で自足するよう書く**（入力コストの主レバー。実測: base全文+research併給 0.8〜1.4M/体 → outline単独 67〜86k/体） |
| 画像（②mockup／④preview） | **画像のみ**（.md 併給禁止） | ②は合成デッキ（後述）、④は preview 全枚。1体が全枚を通しで見る（読書体験の再現。画像1枚≒1.5〜2.5k入力）                                         |

数値の裏取りが要る**数値監査は一致検査**であり、base.md 該当節を参照してよい。

## 評価者の構成（2役＋修正時アドバイザー）

1. **審査員（judge）**: rubric で採点し `verdict` / `must_fix` / `advice` を出す。ループの合否ゲート。
   ルーブリックは**提出先の公式基準があるならそれに忠実に写す**（採択審査なら募集要項の
   審査項目・配点をそのまま）。ペルソナは実読者から逆算（外部選考委員・事業法務DD・意思決定者 等）。
2. **初見読者（fresh reader）**: 予備知識ゼロ・過去版や経緯を知らない設定で対象だけを読み、
   **スライド（節）別に 分かる／引っかかる／分からない** と**素朴な疑問**を返す。採点しない。
   **「分からない」が本編に1枚（1節）以上あれば must-fix 相当としてループ継続**——
   審査員だけを回すと防御的追記が積み上がり可読性が劣化する（2026-08-31 実測）ことへの対抗装置。
3. **アドバイザー（ゼロベース設計者）**: **評価者ではなく修正フェーズの道具**。不合格箇所に
   対し「対象の役割・制約（禁止表現・出典規律）を渡して、**構成案を3つ＋推奨1つ＋根拠**」を
   出させる。fail 箇所だけに投入するためトークン効率が良い（2026-08-31 の S2/S3/S9 再設計で実証）。

スタイリング・可読性の指摘は**全評価者の義務**（デザイン専任ペルソナに分離しない）。
mockup 由来の文字の乱れ・誤字は評価対象外と明記する（③でネイティブ置換されるため）。

## 手順

### 1. 評価計画の提案 ★人間承認必須（計画承認制）

どの段階でも、実行前に次を提案し**人間の承認を得る**。承認なしの評価ループは回さない。
自律ラン（origin-goal 等）では WS の Authorization Envelope に評価計画の事前承認を明記して
往復を省略できる。

| 提案項目       | 内容                                                        |
| -------------- | ----------------------------------------------------------- |
| 対象           | どの段階の何を評価するか（対象単独規約に従う）              |
| 評価者         | 審査員の rubric・ペルソナ／初見読者の有無（既定は両方）     |
| モデル         | 既定は `skill-config.json` `contentEval.models`（変更可）   |
| 合格条件・回数 | 既定は `contentEval.passThreshold` / `maxRounds`（変更可）  |
| **コスト概算** | 概算トークン ≒ 評価者数 × 回数 ×（対象サイズ×1.5＋出力10k） |

### 2. 実行

- 並列サブエージェントで審査員・初見読者を同時実行（互いに独立）。
- **再評価は毎回フレッシュ**: 過去版・過去評価の文脈を与えない**新規** subagent に評価させる
  （同一エージェントの再評価は文脈汚染で甘くなる）。ただし「前回 must-fix の反映検証」だけは
  事実として審査員プロンプトに渡す。
- メインループは評価対象の PNG を Read しない（画像コンテキスト規律・pipeline.md）。

### 3. 判定とループ

- **合格（既定・計画承認で上書き可）**: 各審査員75以上 **かつ** 平均80以上 **かつ**
  重大 must-fix ゼロ **かつ** 初見読者の「分からない」が本編0枚。
- **回数**: 最大3回（`contentEval.maxRounds`）。超過継続は人間承認で +N
  （承認時にコスト再見積りを提示）。
- **収束ガード**: 前巡より指摘が減らなければ上限前でも人間へエスカレーション。
- 不合格箇所の修正: 軽微（A/B 分類・下記）はループ内、設計級はアドバイザーに構成案を出させ、
  採用案を人間が選んでから反映する。

### 4. 正典照合ルール（指摘のトリアージ）

**返ってきた指摘をそのまま反映してはならない。** 正典（outline.md / base.md）と突き合わせて分類する。

| 分類                                                        | 処理                                       |
| ----------------------------------------------------------- | ------------------------------------------ |
| A. 指摘が正典と矛盾し、**正典が正しい**（実装・作図のミス） | ループ内で成果物側を修正                   |
| B. 表記・スタイリング（スライド内で閉じる）                 | ループ内で処理                             |
| C. ロジック・構成など**正典（.md）自体の変更に及ぶ**        | **gate。人間確認を経てから正典を更新する** |

テキスト段階（base/outline）の must-fix 反映は**それ自体が正典変更**なので、反映方針を人間に
提示して承認（まとめてで可）を得てから実施する。**C を AI が勝手に直さない。**

### 5. 記録（永続化）

| ファイル                       | 内容                                                           |
| ------------------------------ | -------------------------------------------------------------- |
| `process/eval_rubric.md`       | 承認済みの審査項目・評価者定義・合格条件・回数上限・コスト管理 |
| `process/eval_results_rN.json` | 第N回の全評価者出力（実測 usage を含める）                     |
| `process/eval_results.json`    | 総括（回ごとのスコア推移・最終判定・反映内容・source_files）   |

## 画像段階の詳細（旧②.5 を吸収）

②の人間承認後〜③の前に、**合成デッキ**を読者評価する（大規模改訂時・重要提出物で推奨）。

- 評価対象は「現行デッキの final render ＋ 改訂分の mockup を、正典の順序で並べたもの」。
  `process/eval_deck/page-NN_<ラベル>.png`（NN は正典の通し順・改訂分は `_v2` 印）。
  幅 1280px 程度に統一。**mockup 単体で評価しない**（前後関係の矛盾が見えない）。
- **読者評価の入力は画像のみ**。ルーブリックにページ順と `_v2` の意味は書いてよい（メタ情報）が、
  outline.md / base.md を併給しない。
- ②の人間承認（構図 verdict 全 ok）を飛ばして画像評価を走らせない——未承認の構図と内容の
  指摘が混ざって分離できない。
- ④収束後の preview に対する読者評価（④.5 の材料づくり）も同じ規約で回せる。

> **実測（2026-08 BAK/YAK デッキ・旧②.5）**: 5ペルソナ × 22枚を opus/medium で並列実行し、
> must-fix 27件・スライド個別指摘 73件（うち構図・ロジック級7件）を**ビルド前に**検出。
> ⑤で出ていれば7枚ぶんの `sNN.js` とアセットが無駄になっていた。

## 出力スキーマ（固定）

自由記述レポートにさせない（集計・差分比較のため）。

**審査員**:

```json
{
  "persona": "審査員名（rubric準拠）",
  "round": 1,
  "scores": [
    { "item": "項目", "score": 0, "max": 0, "reason": "スライド番号を含む根拠" }
  ],
  "total_score": 0,
  "total_max": 100,
  "verdict": "pass|revise",
  "strengths": ["最大3件"],
  "improvements": ["最大3件"],
  "must_fix": ["提出前に直さないと致命的な事項のみ・上限なし"],
  "slide_comments": [{ "page": 0, "comment": "具体的指摘" }],
  "advice": ["次の修正で最も効く助言・最大3件"]
}
```

**初見読者**:

```json
{
  "persona": "初見読者",
  "round": 1,
  "per_slide": [
    { "n": 1, "verdict": "分かる|引っかかる|分からない", "note": "理由1-2文" }
  ],
  "through_line": "通しの所見（線がつながるか・飛躍箇所）",
  "naive_questions": ["素朴な疑問・最大7件"],
  "top_fixes": ["直すと最も効く修正・最大3件"]
}
```

- `slide_comments` / `per_slide` の番号は評価対象の通し順に一致させる。
- 公式配点があるものは満点をそのまま使い、採択下限をプロンプトに書く（合否感覚の接地）。

## やってはいけないこと

- **人間の計画承認なしに評価ループを走らせる**（コストの不意打ち）。
- **AI 審査の合格を人間ゲート（①②④.5）の代理にする。**
- **読者評価にサイド情報（.md 等）を併給する**——画像段階は画像のみ。
- **審査員だけで回す**——初見読者なしのループは可読性の劣化を検出できない。
- **must_fix をそのまま正典へ反映する**（C 分類の gate を飛ばすこと）。
- **同一エージェントに再評価させる**（フレッシュ評価の原則）。
- **メインループで評価対象の PNG を Read する**（画像コンテキスト規律違反）。
- **スタイリング指摘を専用ペルソナに分離する**（全評価者の義務）。

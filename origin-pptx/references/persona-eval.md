# ②.5 ペルソナレビュー

**②の人間承認後・③ネイティブビルドの前**に、モックアップ段階のデッキを想定読者の
ペルソナ（サブエージェント）に評価させ、**ビルド前に内容・構成の欠陥を落とす**工程。

**既定はスキップ。人間が明示的に指示した場合のみ実行する。** 大規模改訂時・
重要提出物（採択審査・経営提案・対外提出）では推奨する。

**この工程が回収するもの**: ④のVLM比較が保証するのは「承認モックアップ通りに施工されたか」
であって、**その構図・ロジックが読者に効くか**は誰も見ていない。従来はそれが⑤の人間レビュー
まで残り、ロジック級の指摘が出ると③の実装ごと捨てることになった。②.5 は同じ指摘を
**pptxを1行も書く前**に前倒しする。

> **実測（2026-08 BAK/YAK デッキ）**: 5ペルソナ × 22枚を opus/medium で並列実行し、
> must-fix 27件・スライド個別指摘 73件を検出。うち構図・ロジック級（＝スライドを作り直す
> 必要があるもの）が7件あり、**ビルド前に潰せた**。同じ指摘が⑤で出ていれば、
> 7枚ぶんの `sNN.js` とアセット生成が無駄になっていた。

## 手順

### 1. 評価計画の提案 ★人間承認必須

AI が次の4点を提案し、**人間の承認を得てから**実行する。承認なしに評価を走らせない
（ペルソナ設計を外すと、大量トークンを使って的外れな指摘だけが返る）。

| 提案項目                 | 内容                                                                              |
| ------------------------ | --------------------------------------------------------------------------------- |
| 審査項目（ルーブリック） | 項目ごとの**定量スコア＋根拠コメント必須**。読者・提出先に合わせて設計            |
| 評価 role（ペルソナ）    | デッキの**実読者から逆算**して割り当てる（審査員・意思決定者・現場・一般読者 等） |
| モデルと effort          | 既定は `skill-config.json` の `evalLoop.personaModel` / `personaEffort`           |
| **コスト概算**           | ペルソナ数 × 対象枚数 × モデルで見積もる                                          |

- **ルーブリックは提出先の公式基準があるならそれに忠実に写す**（採択審査なら募集要項の
  審査項目・配点をそのまま項目にする）。無い場合のみ読者視点で設計する。
- **ペルソナは「デッキに出てくる登場人物」から作る**。デッキが大学・企業・自治体を巻き込む
  座組なら、その各当事者が1ペルソナ。加えて**予備知識のない一般読者**を必ず1体入れる
  （専門用語・図の向き・数字の一貫性はここでしか出ない）。
- **コスト概算の目安**: 1ペルソナが対象枚数ぶんのPNGを読む。5ペルソナ×22枚×opus で
  **40万トークン強**（2026-08 実測レンジ）。枚数とペルソナ数の積で効くので、
  提案時に必ずこの掛け算を人間へ提示する。

### 2. 合成デッキ（eval_deck）の組み立て

**評価対象は「現行デッキの final render ＋ 改訂分の mockup を、正典の順序で並べたもの」**。

```
process/eval_deck/
├── page-01_01_表紙.png                     # 現行 final-01.png のリネーム
├── page-02_02_エグゼクティブサマリー_v2.png  # 今回の改訂分 = mockup 由来
├── page-03_03_課題マクロ.png
└── ...
```

- 命名は `page-NN_<ラベル>.png`。**NN は正典（outline.md / base.md）の通し順**。
  改訂分は末尾に `_v2` 等の印を付け、ルーブリック冒頭で「`_v2` が今回改訂分」と明示する。
- 幅は **1280px 程度に統一**して縮小する（final render も mockup も同じ土俵に載せる。
  原寸のままだと1ペルソナのコンテキストを圧迫する）。
- **mockup 単体で評価しない。** 改訂スライドだけを見せると、前後のスライドとの重複・
  矛盾・ストーリーの断絶が原理的に見えない。②.5 の価値の大半は「並べて初めて分かる指摘」。

### 3. 全ペルソナ共通の必須要件（プロンプトに必ず入れる）

1. **定量スコア（項目ごと）＋根拠コメント**。コメントには**スライド番号を挙げさせる**
   （番号のない指摘はトリアージできない）。
2. **内容面に加えて、スタイリング・文言・可読性などスライドそのものへの指摘を必須とする。**
   これは**全ペルソナの義務**であり、「デザイン担当ペルソナ」に分離しない——
   分離すると、内容ペルソナは崩れたレイアウトを黙って読み飛ばし、デザインペルソナは
   文脈を知らないまま表層だけ見る。読者は常に両方を同時に見ている。
3. **モックアップ由来の文字の乱れ・誤字は評価対象外**と明記する。imagegen 産の文字は
   ③でネイティブテキストに置き換わるため、ここで報告させると指摘が誤字で埋まる
   （④の「何が正典か」を伝える指示と同じ趣旨）。
4. 出力は**スキーマ固定 JSON**（下記）。自由記述レポートにさせない——集計・トリアージ・
   再評価の差分比較ができなくなる。

### 4. 実行

Workflow または**並列サブエージェント**で全ペルソナを同時実行する（ペルソナ同士は独立）。
結果は必ず永続化する:

| ファイル                    | 内容                                                       |
| --------------------------- | ---------------------------------------------------------- |
| `process/eval_rubric.md`    | 承認された審査項目・ペルソナ定義・共通ルール（実行の入力） |
| `process/eval_results.json` | 全ペルソナの出力を配列で連結（トリアージと再評価の入力）   |

メインループは eval_deck の PNG を Read しない（画像コンテキスト規律・`pipeline.md`）。

### 5. 正典照合ルール（指摘のトリアージ）

**返ってきた指摘をそのままスライドに反映してはならない。** 正典（`outline.md` / `base.md`）と
突き合わせて3分類する。

| 分類                                                          | 処理                                       |
| ------------------------------------------------------------- | ------------------------------------------ |
| A. 指摘が正典と**矛盾し、正典が正しい**（スライドの実装ミス） | ループ内で**スライド側を機械修正**         |
| B. 表記・スタイリングの指摘（**スライド内で閉じる**）         | ループ内で処理                             |
| C. ロジック・構成など**正典（.md）自体の変更に及ぶ**          | **gate。人間確認を経てから正典を更新する** |

**C を AI が勝手に直さない。** 正典は人間と合意したテキストの唯一の真実源であり、
ペルソナ（＝模擬読者）の指摘は正典を書き換える権限を持たない。C は「この指摘を受けて
正典をこう変えるがよいか」を人間に提示し、承認後に `outline.md` / `base.md` を更新してから
スライドへ降ろす。

**トリアージ例**:

- 「S07 の矢印の向きが因果と逆に見える」→ **A**（正典の因果は正しい。図が誤訳している）
- 「S05 のキーメッセージが2行に折り返して読みにくい」→ **B**
- 「S22 の主張を支える図がプレースホルダの空箱のまま」→ **A**（正典に図の内容がある場合）
  / **C**（そもそも根拠データを持っていない場合＝主張の再検討）
- 「表紙の連名が、法人の意思決定を経ていないのに対等な連携体に読める」→ **C**
  （事実関係・対外表現の問題。正典と人間の判断が要る）
- 「専門用語（CPF/PSF・RAG）が初見で読めない」→ 用語の注記追加なら **B**、
  用語自体をやめる/言い換えるなら **C**

### 6. ループ（人間の指示があった場合のみ）

- **停止条件**: 人間が承認したスコア閾値に到達、**または最大3回**（`skill-config.json`
  `evalLoop.maxRounds`）。
- **閾値は固定値を持たない。** デッキごとに満点構成もペルソナ構成も違うため、
  毎回1で人間に承認してもらう（例:「審査員 60点満点で 42点以上」）。
- **2巡目以降は変更したスライドのみ再評価する**（④の再検証規律と同じ。全枚を毎巡読ませると
  ペルソナ数ぶん倍で効く）。ただし**ストーリー整合の指摘が出た場合は、その前後スライドも
  対象に含める**（変更の影響が隣接面に及ぶため）。
- ループを回さない運用（1回だけ評価して人間に渡す）も正当。**ループは人間が明示的に
  指示したときだけ**回す。

## 出力スキーマ（固定）

各ペルソナは次の JSON オブジェクトを1つ返す。`eval_results.json` はその配列。

```json
{
  "persona": "【審査員】YAK 外部有識者審査委員（公式ルーブリック）",
  "scores": [
    {
      "item": "社会性",
      "score": 8,
      "max": 10,
      "reason": "S03/S04 で調査費不足の構造を定量で示せている。ただしS09の市場規模が…"
    }
  ],
  "total": "53/80（共通審査項目 41/60・地域経済活性化加点 12/20）",
  "strengths": ["…", "…", "…"],
  "improvements": ["…", "…", "…"],
  "must_fix": ["提出前に必ず直すべきもの（件数の上限は設けない）"],
  "slide_comments": [{ "page": 7, "comment": "矢印の向きが因果と逆に見える" }]
}
```

- `strengths` / `improvements` は**各3件以内**（絞らせないと総花的な感想文になる）。
- `must_fix` は上限を設けない。**「提出前に必ず直すべきもの」だけ**を入れさせる。
- `total` は満点表記込みの文字列（配点構成がペルソナごとに違うため数値固定にしない）。
- `slide_comments` の `page` は eval_deck の `page-NN` に一致させる。

## ルーブリック例（`eval_rubric.md` の形）

冒頭に**評価対象・共通ルール**を書き、以降ペルソナごとに項目を並べる。

```markdown
# eval_rubric.md — 5ペルソナ評価ルーブリック（YYYY-MM-DD）

評価対象: `process/eval_deck/page-01〜22.png`（現行デッキに改訂スライドを差し込んだ合成デッキ。
ファイル名 `_v2` が今回改訂分）。
共通ルール: 各項目を **1〜5点**（審査員のみ公式配点）で採点し、**点数の根拠を1〜2文**で書く。
スライド番号を挙げて具体的に。最後に「強み Top3」「改善点 Top3」「must-fix」を出す。
**内容だけでなく、スタイリング・文言・可読性などスライドそのものへの指摘も必ず含める。**
モックアップ由来の文字の乱れ・誤字は評価対象外。

## ペルソナ1: 審査員（外部有識者・公式ルーブリック）

- 社会性 /10・新規性 /10・市場性 /10・実現可能性 /10・連携の必要性 /10・支援の必要性 /10
- 視点は募集要項の審査基準に忠実に。60点満点の6割（36点）が採択下限。

## ペルソナ2: 大学（研究者・TLO/URA・大学経営の3視点）

1. 研究者: 参加したいか（フィードバック・社会実装機会の魅力）/5
2. TLO/URA: empower と感じるか、仕事を奪われると感じるか /5
3. 大学経営: 収益・ポートフォリオのメリットが伝わるか /5
4. 関与表現の適切さ: 承諾状態の記載が実態に忠実か（過大表記がないか）/5
5. 参加負担の明確さ・軽さ /5

## ペルソナ3: 企業 / ペルソナ4: 自治体 / ペルソナ5: 一般

（同様に5項目×5点。一般ペルソナは「ストーリーの一貫性」「1枚1メッセージ」
「専門用語」「図の可読性」「数字の一貫性」を固定で持たせるとよい）
```

- **1体のペルソナに複数視点を持たせてよい**（例: 大学＝研究者・URA・経営）。
  当事者組織の中で利害が割れる場合、視点ごとに項目を切ると指摘が具体化する。
- 採択審査など**公式配点があるものは満点をそのまま使う**（1〜5点に丸めない）。
  採択下限（例: 6割）をプロンプトに書くと、スコアが合否感覚に接地する。

## やってはいけないこと

- **②の人間承認を飛ばして②.5 を走らせる**。構図が未承認の面を評価しても、
  指摘が構図の未承認部分と混ざって分離できない。
- **人間の指示なしに既定で走らせる**。トークン消費が大きく、既定スキップが正しい。
- **評価計画（ルーブリック・ペルソナ・コスト）の人間承認を省く。**
- **mockup 単体を評価対象にする**（前後関係の矛盾が見えない）。
- **must_fix をそのまま正典へ反映する**（C分類の gate を飛ばすこと）。
- **メインループで eval_deck の PNG を Read する**（画像コンテキスト規律違反）。
- **スタイリング指摘を専用ペルソナに分離する**（全ペルソナの義務として持たせる）。

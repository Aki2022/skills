# パイプライン詳細

`SKILL.md` の概要を、各ステップの入出力・コマンド・人間チェックポイントまで具体化したもの。設計背景・PoC実測結果は元プロジェクトの `docs/specs/pptx-generation-v2.md` を参照（この文書はその決定事項をスキルとして再構成したもの）。

## 核心原則（再掲）

- ネイティブ層（PptxGenJS）＝ レイアウト・箱・矢印・日本語テキスト。完全編集可能。
- image_gen 層＝ アイコン・イラスト・背景を**文字なし**アセットとして生成し埋め込み。
- モックアップ（②）は仕様（スペック）であり、そのまま転写するソースではない。デザインの意思決定は②で完結させ、③以降はやり直さない。
- **②完了前に③を開始しない（直列厳守）**。②と③を並行させると「同じoutlineから別々に作った2つの成果物」になり、モックアップとPPTXが大きく乖離する（2026-07-08のROAデッキで実証された失敗）。③は必ず生成済みモックアップを目視で仕様として読み取ってから書き、④の照合ループを省略しない。時間短縮したい場合に並行してよいのは「②の実行」と「③の共通部品（chrome関数等）の準備」まで。スライド本文の実装はモックアップを見てから行う。

## ⓪ 画像生成スタイルガイド

**入力**: なし（このスキルの `style-guide/` が固定の入力）
**出力**: なし（読むだけ）

`style-guide/tokens.json`・`style-guide/layout-grammar.md`・`style-guide/imagegen-prompt-convention.md` を読み、以降の②③で使うトークン値・レイアウトパターン・プロンプト規約を把握する。プロンプトは保存し、デッキ内で再利用する（Visual Direction Preambleは逐語再利用が規約）。

## ① 素材投入 → outline.md 共同作成

**入力**: ユーザーから渡される素材（既存資料・要点メモ・口頭指示など）
**出力**: `outline.md`（テキストの Single Source of Truth）

- 各スライドは **title（=tracker）と keyMessage を分離したフィールド**で持つ（v3意味論、layout-grammar.md）:
  - **title**: 簡易な章タイトルの**名詞句 or 疑問形**（例:「課題は？」「導入効果」）
  - **keyMessage**: **必ず1行**。タイトルが疑問形ならその回答
- **①完了前の必須チェック（ストーリーテスト）**: 全スライドの keyMessage だけを上から順に並べて
  読み上げ、**それだけでストーリーとして成立するか**を人間と確認する。成立しないなら outline を
  直してから②へ進む（④で直すより桁違いに安い）。あわせて各 title の形式（名詞句/疑問形）と
  keyMessage の1行制約もここで機械的に確認する。
- 1スライド1メッセージ。**takeaway box・バンパーステートメントに相当する行を outline に書かない**。
  説明詳細は本文フィールドか「右1/3箇条書き」（ContentText型）として構造化する。
- 使うレイアウトパターン（layout-grammar の基本型）をスライドごとに決める。
- 文字量はレイアウト文法の目安（ノード見出し最大8字、箇条書き本文最大40字×2行 等）を守る。守らないと③のネイティブビルドでオーバーフローが起きやすい。
- フォントは**全デッキ一律 BIZ UDPGothic**（2026-07-28決定・ユーザーへの確認不要。
  mac/share 2プロファイル制は Hiragino Sans W4 がPowerPoint実機で解決されず廃止）。
  ③の `mk({font: "BIZ UDPGothic"})` に渡す。表紙有無・フッター日付はこのタイミングで聞く。
- 人間と内容を確認しながら書く。**このファイルが最終テキストの唯一の出典**であり、以降どのステップで生成される画像・モックアップの文字も参照しない。

実例形式:

```markdown
# スライド: 導入までの3ステップ

パターン B（図解型）。960×540pt / 16:9 キャンバス。左から右へ3ステップのプロセスフロー。

## タイトル（tracker）

導入プロセス

## キーメッセージ（1行）

導入は申込み・審査・承認の3ステップで最短2週間

## ステップ

1. **申込み** — オンラインで申込書を送信
2. **審査** — 書類確認と与信審査
3. **承認** — 契約締結とアカウント発行

## 構図メモ

- ノード3個（角丸四角形）を横並びに配置、ノード間を矢印コネクタ2本で接続。
- 各ノード内部: 上部に番号バッジ、中央に見出し、下部に補足1行。
```

## ② デザインモックアップ生成 ★人間チェックポイント

**入力**: `outline.md` の該当スライド + `style-guide/imagegen-prompt-convention.md` の規約
**出力**: `mockup_<slide>.png`（フルスライドのラスタ画像。デザイン仕様書として扱う）

1. `imagegen-prompt-convention.md` の7要素構成（Visual Direction Preamble → Aspect指定 → Layout Pattern指示 → Slide Content → Color Usage → Style Directive → Negative constraints）でプロンプトを組み立てる。
   - **実データチャートのスライドは、②で数値を描かせない**。チャート領域は「空のラベル付き
     プレースホルダ枠」にする（`imagegen-prompt-convention.md §11` / `chart-rules.md`）。imagegenは
     数値を捏造するため、②で描くと人間が捏造値をレビューしてrejectに至る（2026-07-10実証）。
     実データの図は③で `scripts/build_chart_svg.py` 等でネイティブ描画する。
2. 安全モードで実行する（**AI が直接実行できる**。`references/image_gen.md` のAUTHORIZATIONルール参照）:
   ```bash
   codex exec --sandbox workspace-write -c sandbox_workspace_write.network_access=true --cd "$PWD" "<組み立てたプロンプト>"
   ```
3. 生成物を `$CODEX_HOME/generated_images/` から find してワークスペースへコピー（`references/image_gen.md` のSAVE-PATH GOTCHA参照）。
4. **★人間がモックアップをレビューし、デザイン意思決定を完結させる**。この時点で構図（ノード数・配置・余白バランス・トーン）が確定する。③以降はこのモックアップの構図をそのまま実装するだけで、デザインをやり直さない。レビューは下記の**チャット対話式レビューループ**で実施する。

### ②のレビュー手順: チャット対話式レビューループ

Webサイト・トンネル等の追加インフラは使わない。チャット（Claude アプリのセッション同期によりモバイルからも同じ会話で回答可能）で1枚ずつ収集する。

> **人間が `process/` を直接見て一括フィードバックする運用も許容する**（2026-07-10の実運用）。
> その場合「1枚ずつ送信」は省き、返ってきた複数枚ぶんの修正を `feedback.json` にまとめて記録し、
> `verdict: revise` の分だけ1バッチで再生成する。要は「未回答分だけ再開できる」状態を保てばよい。

1. エージェントが `process/` の `mockup_*.png` を**スライド順に1枚ずつチャットに送信**し、毎回「S3/20: OK？修正コメントある？」と短く質問する（1メッセージ1枚。まとめて送らない）。送信はファイル添付（表示）であって**エージェント自身が画像をReadする必要はない**（下記「画像コンテキスト規律」参照）。
2. 人間は「OK」または修正コメント（例:「グラフの色をtone準拠に」）を返信するだけ。
3. エージェントは回答を受けるたびに `process/feedback.json` へ逐次記録する。中断してもこのファイルから未回答分だけ再開できる。

   ```json
   {
     "deck": "yyyymmdd_内容",
     "reviewed_at": "YYYY-MM-DD",
     "slides": [
       { "slide": 1, "file": "mockup_01.png", "verdict": "ok", "comment": "" },
       {
         "slide": 2,
         "file": "mockup_02.png",
         "verdict": "revise",
         "comment": "グラフの色をtone準拠に"
       }
     ]
   }
   ```

4. 全件回収後、`verdict: revise` の分だけを**まとめて1回の codex バッチ**（タスクファイル方式）で再生成する（下記トークン運用規則の「差し戻しは1セッション」に準拠。単発実行禁止）。
5. 再生成した画像のみ、もう一巡同じ手順でレビューする。全件 `ok` になったら②完了 → ③へ進む。

## ③ ネイティブビルド

**入力**: `outline.md`（テキスト）+ 承認済みモックアップ（構図の仕様）+ `style-guide/layout-grammar.md`（座標）+ `style-guide/tokens.json`（色・サイズ）
**出力**: `output.pptx`（完全ネイティブ編集可能）+ 埋め込み用アイコン/イラストPNG

**実施形態（必須）**: メインループは画像を読まない規律があるため、③は**スライドごとの
ビルダーサブエージェント（Sonnet）**で行う。ビルダーへの指示には**「サブエージェントを起動せず、
自分の Read/Write/Bash で直接実行せよ」を必ず含める**（2026-07-14: 明記しなかったビルダーが
作業を孫エージェントに丸投げしようとして空手で停止した）。各ビルダーに「そのスライドの承認済み mockup_NN.png
＋ outline.md 該当節 ＋ 共通ヘルパ（`scripts/deck_helpers.js`）」を渡し、**mockupを目視で仕様として
読み取ってから**スライドモジュール（`slides/sNN.js` のような分割ファイル）を書かせる。
outline/mockup_task の**テキストだけから誰も mockup を見ずに組むのは禁止**——テキストは構図の
近似でしかなく、2026-07-10 に24枚中18枚が承認モックアップと別物になった実失敗がある。
分割ファイルにするのはビルダーを並列実行しても衝突しないため。

1. `scripts/deck_helpers.js` を土台に、**スライドごとのモジュール `slides/sNN.js` へ分割**して組む（1枚岩の
   build_deck.js だと並列ビルダーが同一ファイルを奪い合うため）。分割は `scripts/split_deck.py`、薄い
   エントリが共有 ctx を作り `require('./slides/sNN.js')(ctx)` で束ねる。各ビルダーへは
   `references/builder_brief.template.md` を `builder_brief.md` にコピーして渡す（正本優先順位を明文化）。
   （1枚ものは `scripts/build_slide.example.js` 参照）
2. レイアウト文法の該当パターンの%座標を720×405pt換算のpt値に変換して配置する（imagegenプロンプトと同じ座標系を使っているため、モックアップとのズレが出にくい）。
3. カード・矢印などの図形要素はPptxGenJSのShape（`roundRect`, `rightArrow` 等）で組む。矢印は**塗りのShape**を使う（細い線コネクタより視認性が高いことがPoCで確認済み）。
4. **アセット生成はモックアップに写っている限り必須工程**。運用は2段: (a)**標準アイコン語彙**
   （builder_brief記載の共通セット）を先行バッチで生成しつつ、(b)ビルダー完了報告の
   「不足アセット」を集約して**ギャップ追加バッチ**を1回流す（2026-07-14実証: 事前語彙17個＋
   ギャップ5個の2段で、語彙外アイコンの意味ズレをVLM指摘前に潰しきれなかった反省を含む。
   ビルダーには語彙に無いアイコンのファイル名を発明させず、報告だけさせる）。プロンプト末尾に "NO text, no labels" を必ず付ける。省略すると「アイコン全滅」という最大クラスの構図乖離になる（2026-07-10実証）。**生成したラインアイコンは埋め込み前に必ず `scripts/normalize_icons.py` で正規化する**（白背景透過＋navy単色化。生のままだと白ボックス露出＋線が淡く視認不良になり2周した／`references/image_gen.md`）。同じ保存先コピー処理が必要。
5. テキストは `outline.md` からそのまま流し込む（モックアップの文字は参照しない・OCRしない）。事前指定画像（スクショ等）の**内容**は `input/` 原本が正——mockupが別画面を描いていても原本を使い、構図・注釈デバイスだけmockupに合わせる。
6. **ビルド直後に `scripts/sanitize_pptx.py output.pptx` → `scripts/set_fonts.py output.pptx`
   を必ずこの順で実行**（sanitizeは修復エラー矯正・set_fontsは BIZ UDPGothic への統一。
   どちらも冪等。gotchas §16-17・tokens fontFamily）。
7. **④合格後・⑤前に `scripts/inject_template.py output.pptx <skill>/style-guide/template_v3.pptx
<最終成果物>.pptx` で最終成果物化**（テンプレ注入 Phase 1）。会社テンプレ由来の master/layouts/
   theme が土台になり、人間が「新しいスライド」で会社レイアウト11種を使える・テーマの色に 44546A が
   並ぶ・ページ番号/日付はスライド直描きのため保たれる・コピーライトはテンプレ側レイアウトから表示。
   注入後は **`set_fonts.py` を最終ファイルへ再適用**（テンプレ由来のレイアウト・マスター・テーマの
   フォントも BIZ UDPGothic に統一される）→ 1回レンダして注入前と同一であること＋
   `sanitize_pptx.py --check` を確認してから⑤へ。

## ④ 検証ループ（上限5回・skill-config.json で変更可）

**入力**: `output.pptx` + 承認済みモックアップ
**出力**: 検証済み `output.pptx`、またはさらなる修正が必要な場合は③へ差し戻し

> **よくある誤用**: 欠陥QA（あふれ・豆腐・衝突探し）だけ回して④を済ませたことにする。
> 欠陥QAは下記2の決定的チェックの一部でしかなく、**④の合格条件は3のmockupペア比較まで含めて**
> 成立する。「壊れていない」と「承認したデザインである」は別の保証（2026-07-10: 欠陥QAのみで
> ⑤へ進め、18枚の構図乖離が人間まで素通りした）。

各イテレーション:

1. **レンダリング**:
   ```bash
   soffice --headless --convert-to pdf --outdir . output.pptx
   pdftoppm -png -r 150 output.pdf preview
   ```
2. **決定的チェック（先に実施、コストゼロ）**:
   - テキストオーバーフロー（ボックス外にテキストが溢れていないか）
   - フォント置換の有無（`a:ea` が BIZ UDPGothic になっているか＝set_fonts適用漏れ検出、
     豆腐化していないか。事前に `fc-list | grep -i "biz ud"` でフォント存在を確認）
   - 要素がキャンバス端・セーフマージン（42pt）を侵していないか、本文最下端が y≤500pt か
   - **v3スタイルのXML機械検査（python-pptxで、VLMに頼らない）**:
     タイトルが名詞句/疑問形か・**キーメッセージが33字以内か**（34字以上は28ptで折返す。
     文字数はXMLから機械計測できる——1巡目のVLM待ちで見つけるより桁違いに安い）・フッター日付/ページ番号/縦書き
     コピーライトの存在・数字/単位の50%比率（ラン混在）・下段にtakeaway box相当の箱がないか・
     表が addTable 由来のネイティブ表か（図形模造でないか）
   - **PowerPoint修復エラーの機械検出**: `python3 <skill>/scripts/sanitize_pptx.py output.pptx --check`
     が OK であること（pptxgenjs のチャートXMLスキーマ違反・slideNumber不正プレースホルダ。
     LibreOffice/python-pptxでは検出できない。ビルド直後に非checkモードで矯正済みのはずで、
     ここはその確認。gotchas §15-16）
   - **欠落アセットの機械列挙**: ビルドスクリプトの `addImgIfExists` 相当が省略した画像ファイル名を必ずログ出力させ、欠落一覧を確認する（「グレースフル省略」は起動失敗を防ぐ仕組みであって、欠落したまま⑤に進んでよいという意味ではない。欠落があるなら生成するか、省略を人間が明示承認する）
3. **VLM構図比較（決定的チェック通過後のみ・2段階）**:
   - **1段目（優先順位付けスクリーニング・任意）**: 枚数が多い場合、preview全枚とmockup全枚をモンタージュ化して1回のサブエージェント比較で乖離候補を挙げ、2段目の**着手順**を決める。
     - モンタージュのタイル幅は**1枚あたり600px以上**（縮小しすぎるとコールアウト位置・表の行高・文字揃えが物理的に見えなくなる。2026-07-08のPMDAデッキで400px幅が「乖離なし」誤判定を出した実証あり）
     - **スクリーニングは合格判定に使ってはならない**。「乖離なし」と返ってきても2段目は省略しない（優先順位付け専用）
   - **2段目（全スライド必須のペア精査）**: **全スライド**について、preview 1枚＋mockup 1枚のペアをフル解像度で使い捨てサブエージェントに比較させる。デッキ完成までに最低1巡は必須（反復2回目以降は変更したスライドのみでよい）。
     - **プロンプトは敵対的に書く**: 「一致しているか判定して」ではなく「**あら探しをして差分を列挙して**。レイアウト/欠落・追加/配色・フォント/テキストの4カテゴリで、差分が本当に無いカテゴリのみ『なし』と書け」。確認型の聞き方はAIを追認に流す（同一画像ペアで確認型=見落とし・敵対型=全件検出、の差が実証済み）
     - **チェッカーに例外判断を委ねない**: 「アイコン欠落は想定内だから無視して」等の免罪符を渡さない。チェッカーは差分を全て報告し、想定内かどうかはオーケストレーター/人間が判定する（免罪符は関連する構図崩れまで一緒に握り潰される）
     - **オーケストレーター自身も免罪符を乱発しない（2026-07-11 差し戻し実証）**: チェッカーが正しく報告した差分を、オーケストレーターが「装飾差・商標回避・正規化規約だから意図的」と一括分類して修正対象から外した結果、人間レビューで「全く再現されていない・全体的に品質が低い」と差し戻された。意図的差分として却下してよいのは**個別に理由を明文化できるものだけ**で、迷ったら修正側に倒す
     - **品質印象を独立の合格基準にする**: 「mockupと構図が一致するか」に加えて「**人間が見て洗練されて見えるか**」をチェッカーへの明示の問いに含める。タイトルの迫力不足・アイコンの存在感不足・空パネルの未完成感は構図一致チェックでは検出されない（判定語彙の目安: MAJOR=人間が『作りかけ/崩れてる』と感じる、MINOR=気づくが許容）
     - **quality=low アセットの品質リスク**: モックアップはlowでよいが、人物イラスト・UIモック等の「密度が品質に直結するアセット」は**high**で生成する（gotchas §13。lowの人物は縮小時に無個性なシルエット化する）
     - **並列実行が既定**: ペア比較サブエージェントは互いに独立なので、**必ず並列バッチで投げる**
       （1体1ペアの画像コンテキスト規律とも整合。逐次実行は時間の無駄）。
     - **シャーディング・レシピ（2026-07-10 実証で有効だった形）**: 検証エージェントは**1体あたり約6スライド**に分けて並列で回す（24枚なら4体）。各エージェントは担当ペアを敵対比較し、**スライドごとに MATCH / MINOR / MAJOR の判定語彙**で返す。MAJOR/MINORだけを集約 → 修正 → **変更したスライドのみ再検証**（同じ6枚単位）。
     - **icon-legibility を独立チェック項目にする**: 「アイコンが淡色/線細で視認不良になっていないか」「濃色セルの navy アイコンが白チップ無しで消えていないか」を明示的に問う（薄いアイコンは通常の構図比較だと見落とされやすい・2026-07-10に2周した）。フッター下端clip（§gotchas）も定型チェックに入れる。
4. 差分があれば③のPptxGenJSスクリプトを微修正（座標・フォントサイズ・カード幅など）して1へ戻る。**画像を丸ごと再生成しない**（コスト・時間の両方で非効率）。
5. **ループ規律（上限5回・2026-07-13改訂）**: 合格したら即終了（上限まで回さない）。2巡目以降は
   **修正したスライドだけを再検証**する（毎巡フルスキャンしない——これで上限を上げても収束済み
   デッキのコストは増えない）。**発散ガード**: 前巡より未解消差分が減っていなければ、上限前でも
   打ち切って人間にエスカレーションする（構図自体の見直し＝②へ戻るべきケースの可能性が高い）。
   5回で収束しない場合も同様に⑤で人間に判断を委ねる。

**⚠️ ③の再整合義務**: ②のモックアップを（差し戻し・作り直し等で）再生成した場合、**既存のビルドスクリプトは旧仕様の実装物**である。「実装済みだから」と流用せず、新しい承認済みモックアップを仕様として③を読み合わせ・修正してから④に進む（2026-07-08のPMDAデッキで、旧モックアップ基準のbuild_deck.js流用＋甘いチェックの複合により、コールアウト位置・表の行高・文字揃え等の乖離が⑤の人間レビューまで素通りした失敗の再発防止）。

## ⑤ 人間最終レビュー → クリーンアップ

**入力**: 検証済み `output.pptx` + 最終プレビューPNG
**出力**: 承認 または 差し戻し指示

最終成果物を人間が確認する。ここでの差し戻しは、通常③の微修正で対応するが、構図自体の変更が必要な場合は②からやり直す。

**承認後のクリーンアップ（必須・承認がトリガー）**: 人間の最終承認を受けたら
`scripts/cleanup_deck.py <デッキdir>` を dry-run で提示し、承認後に `--apply` で実行する。
役割を終えた中間生成物（mockup/preview/PDF/ログ/node_modules/残骸dir）を削除し、
**修正時の再構築に必要なもの（outline.md・slides/・assets/・process/output.pptx 等）は残す**。
タイミングが重要: **修正サイクル中に消すと修正のたびに再生成オーバーヘッドが生じる**ため、
承認前には絶対に実行しない。逆に承認後に放置するとデッキごとに50MB超の残骸が積もる。

## コスト・効率化の注意（15枚デッキ想定）

- モックアップimagegen: 概算 $2〜3（サブスク内消費）
- 文字なしアセット生成: 概算 $0.5〜1（サブスク内消費）
- Claudeトークンの主消費はVLMによる構図比較（④）
- ネイティブ方式は修正がHTML/PptxGenJS編集で完結するためコスト効率で優位（画像丸ごと再生成方式は修正のたびに再課金が発生する）

効率化の方向性:

1. **スライド単位でサブエージェントを分離**し、プロンプトキャッシュを効かせる（デッキ全体を1エージェントで逐次処理しない）。
2. チェックを階層化する: 決定的チェック → VLM → 人間（安い/速い順に先に倒す）。
3. 承認済みビルドスクリプト（PptxGenJSコード片）を資産化し、次のデッキで再利用してコストを逓減させる。
4. 複数スライドのプレビューをモンタージュ形式で一括レビューし、往復回数を減らす。

## Claude側のモデル・トークン運用規則

### モデル使い分け

**実行時の割当は `style-guide/skill-config.json` が正典**（⓪で読む。下表は既定値の背景説明）。
変更したい場合は config を編集する——本文のハードコードを書き換えない。

| 作業                                                   | モデル                  | 理由                                                     |
| ------------------------------------------------------ | ----------------------- | -------------------------------------------------------- |
| 検収（要素個数・余分要素・tone色のチェックリスト照合） | Haiku サブエージェント  | 機械的照合。視覚入力可で最安                             |
| ビルドスクリプト作成・修正 / outline下書き             | Sonnet サブエージェント | モックアップを仕様として読む中核作業                     |
| VLM構図比較（④の1段目・2段目とも）                     | Sonnet サブエージェント | 差分の言語化が必要（Haiku非推奨）                        |
| オーケストレーション・設計判断・人間との対話           | メインループ            | 上位モデルは温存し、機械的作業をサブエージェントに下ろす |

- サブエージェントは使い捨て（1タスク1エージェント）にし、安定した指示文＋最小の画像入力で呼ぶ（プロンプトキャッシュが効く形）。
- 実行環境がサブエージェントの effort 指定に対応している場合、検収・機械的作業は low、VLM精査は high を目安にする。
- imagegenの品質2段階（low下書き→high最終）は imagegen-prompt-convention.md §9 を参照。

### 画像コンテキスト規律（Claude側の最大コスト源）

画像はテキストの数十倍のトークンを消費し、メインループの文脈に読み込んだ画像は以降の全ターンで入力トークンとして課金され続ける。20枚デッキではここが支配的なコストになる。

- **メインループは mockup / preview / anchor のPNGを原則 Read しない**。チャットレビューループでの画像送信はファイル添付（表示）であり、Read は不要。
- VLM比較・検収は**使い捨てサブエージェント**で行い、そのエージェントには比較対象（preview 1枚＋mockup 1枚、または montage 2枚）だけを読ませる。デッキ全枚数を1つの文脈に読み込まない。
- アンカー画像・スタイルガイドの参照が必要な場合も、同一サブエージェント内で1回だけ読み、以降は文脈内のものを使い回す。
- 例外（メインループが画像を見てよい場合）: 人間との対話で当該画像の内容を直接議論する必要がある時のみ。その場合も対象の1枚に限る。

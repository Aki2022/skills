# Plugin Resolver

**倉庫がこのロジックを持つ理由**（決定7）: 工場側に置くと同じ規則が複数実装になり、
`extends` の解釈がズレる余地が残る。ズレは仮定ではなく実測済み — 同一ブランドの値が
2箇所で完全に別物だった。

## 選択の手順

1. `plugins/*/plugin.yaml` をスキャンし、`supported_media` に対象媒体を含む箱を候補にする。
2. `priority.contexts` のうちタスク文脈に一致するスコアが最も高い箱を選ぶ。
   文脈一致が無ければ `priority.default` を使う。
3. **同点のタイブレーク**: (a) プロジェクトローカルに近い箱、(b) それも同点なら id の辞書順で先。
   決めきれない・候補が拮抗する場合は**ユーザーに確認する**（黙って選ばない）。
4. `extends` があれば親を**1階層だけ**辿って合成対象に含める。

## `extends` は1階層で止める

```yaml
extends: [digital-agency]   # 親1個・1階層のみ。多段継承は不可
```

合成の向きは**子が親を上書き**する。親の原則（アクセシビリティ・公共性等）は継承され、
子の意匠（配色・タイポ）が優先される。

**なぜ1階層に限るか**: 多段にすると「どの値がどこから来たか」が追えなくなり、
ライセンスゲートの判定（どの箱の資産か）も曖昧になる。

## 受け入れテスト

**このテストは退役した `examples/tasks/uc-02-my_company-pptx.md` から引き継いだもの**
（2026-09-09）。元は pptx の利用例の形をしていたが、**検証している規則は媒体に依存しない**ため
媒体中立に書き直して倉庫側へ移した。元ファイルは pptx 固有の運用例だったので退役した。

### T1: 1階層継承が働き、多段継承が起きない

- 入力: 文脈 `corporate-presentation`、箱を `my_company` と明示指定。
- 期待:
  1. Resolver が `my_company` を選ぶ。
  2. `my_company` の `extends: [digital-agency]` により、**親 digital-agency の原則が
     合成対象に含まれる**。
  3. digital-agency がさらに親を持っていたとしても、**その親は合成されない**（1階層で停止）。
  4. 合成の結果、値の競合は**子（my_company）が勝つ**。
  5. 報告に「使用した箱と継承元」が出る（`my_company ← digital-agency`）。

### T2: ライセンスゲートが等級と独立に働く

- 入力: `observed` の箱（`digital-agency`）を指定し、資産値（tokens 実値）を要求。
- 期待: `usage_policy.license_gate_approved` が `true` のときだけ実値を返す。
  `false` なら**原則プローズは返すが実値は返さない**。等級が `observed` であること自体は
  可否の理由にならない（ゲートは直交する属性）。

### T3: 取得メタの欠落を黙って通さない

- 入力: `tier` または `source` を欠いた箱。
- 期待: 検査が**赤**になる（`scripts/` の validator。ISSUE-04）。
  「メタが無い＝上流を追えない」であり、上流が流動的である前提と両立しない。

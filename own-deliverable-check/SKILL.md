# own-deliverable-check — 成果物の検査の入口

成果物の検査の**ルーター**（確かめる対象は layer ではなく成果物なので、名前に layer の語を使わない）。検査そのものは持たない。持つのは 3 つだけ:
**対象の判定・カバレッジ表・実行順序**。

## なぜルーターが要るか

導入済み skill は 59 個あり、デザイン検査に関わるものだけで 9 個ある。
個別名を覚えるのは現実的でなく、文脈発火（description の文字列マッチ）は
発火しなかった skill が**沈黙する** — 呼ばれなかったことは誰にも見えない。

このルーターは逆の契約を結ぶ: **実行しなかった検査を、理由つきで必ず報告する。**
漏れをゼロにはできないが、漏れを**見える**ようにはできる。

## 手順

### 1. 対象を判定する

| 対象          | 判定の手がかり                                      | 扱い |
| ------------- | --------------------------------------------------- | ---- |
| LP            | 広告流入前提・CV（ボタン/フォーム）がある単一ページ | 手順 2 へ |
| プロダクト UI | ログイン後の画面・ダッシュボード・操作が主目的      | 手順 2 へ |
| 資料          | スライド・PDF・レポート・HTML 文書                  | 手順 2 へ |
| 判定できない  | 上のどれとも決められない・複数に当てはまる          | 検査を始めずに止まって聞く。聞けない実行（無人）なら、対象を確かめていないと報告して終える |

判定できない対象を LP として検査しない。LP の検査を当てると、当たらない規則の結果まで合格・失格として報告され、
黙って間違う（以前の既定はこれだった）。

### 2. 前提とカバレッジ表

web対象は git toplevel の `ux/design/` を確認し、`own-design-author` のL0を実行する。
不在・失格なら生成や非決定論レビューへ進まず、定義の整備へ戻す。L0/L1は確認不要、
L2の描画検査は人間に実施可否を確認する。対象0件は失格で、準拠合格にしない。
pptxは従属WS完了までux/design/を読まないため、その制約を報告する。

**この表がこの skill の本体。** 空欄は「担当が存在しない」ことの明示であり、
検査を実行できない観点は報告にもそのまま**欠落**として書く。

| 観点                             | LP                                      | プロダクト UI                                                        | 資料                                                |
| -------------------------------- | --------------------------------------- | -------------------------------------------------------------------- | --------------------------------------------------- |
| 構造（優先度と描画後の位置） | LP は outline の順序と文言の一致（`infoarch-author dom`） | `own-web-build` の `audit_screen.py`（blueprint の優先度と、実ブラウザで測った位置。PC とスマホの 2 つの幅） | 対象外 |
| 骨格（主操作・領域の印） | 対象外 | 同スクリプト（主操作が 1 つだけ塗られている・宣言した領域がすべて描かれている・印が 0 件なら「確かめていない」） | 対象外 |
| 状態（loading・empty・error など） | 対象外 | 同スクリプト（宣言した状態が、宣言した文言でページにある） | 対象外 |
| 審美・レイアウト実測（決定論）   | `own-web-build` の `measure_render.mjs`（`--profile lp`） | 同じ道具（`--profile product-ui`。`fold-cta` はプロファイルが当てない） | HTML資料はL0/L1/L2。pptxは `own-pptx-build` の既存決定論検査（ux/design/連携は未カバー）。印刷のプロファイルは無い（印刷の build を始めるとき） |
| マーケ定性（独立レビュアー採点） | `own-website-audit` の rubric           | **欠落**                                                             | **欠落**                                            |
| 広告審査・法務・SEO・計測        | `own-website-audit`                     | `own-website-audit`（該当節のみ）                                    | 対象外                                              |
| UI ガイドライン準拠              | `web-design-guidelines`                 | `web-design-guidelines`                                              | 対象外                                              |
| アクセシビリティ修正             | `fixing-accessibility`                  | `fixing-accessibility`                                               | **欠落**（validator の自己点検のみ）                |
| 表示性能（Core Web Vitals）      | `web-perf`                              | `web-perf`                                                           | 対象外                                              |
| AI 生成様式の検出                | `baseline-ui`                           | `baseline-ui`                                                        | **欠落**                                            |
| ブランド一貫性                   | `ux/design/` のL0と解決済みマニフェストによるL1/L2 | 同左 | HTML資料は同左、pptxのux/design/準拠は未カバー                                                |
| 正式名称・固定値（辞書）         | `own-doc-update` の `dictionary.py check-html`（`docs/dictionary/` のゆれ・印の値・期限切れ） | 同左 | HTML資料は同左、pptxは未カバー |

補足:

- 描画後の実測の道具は 1 つ（`own-web-build` の `measure_render.mjs`）。何を当てるかは成果物の型ごとのプロファイル
  （`own-design-author` の `references/measurement-profiles.json`。当てる検査・当てない検査と理由・幅と配色）が決める。
  結果の `measured` は実際に測った件数で、0 件・実行の失敗・プロファイルが無い型は合格にしない。
- `own-website-audit` は外部基準とマーケの採点だけを持つ。LP のときは、実測が緑になってから `own-website-audit` を呼ぶ。
- 重複 skill の検出は `own-skill-commonize` の `skill_lint.sh`（S7）が担う。
  `source-command-*` の対応先は現在の正典には存在しない（2026-10-12 確認）。
  ルーターは常に通常名（`baseline-ui` 等）を使う。
- 対象外のデザイン系 skill: `dataviz`（チャートの配色・作成指針で、検査ではない）と
  `artifact-design`（Claude Artifacts の作成指針）は、どちらもこの repo の正典に実体が無く
  アプリ側で提供される。検査のカバレッジ表には載せない。

正式名称・固定値（辞書）の行は、HTML の成果物ごとに `python3 <skills>/own-doc-update/scripts/dictionary.py check-html <repo> <file.html>…` を流す。repo の `docs/dictionary/` が語と値の唯一の出どころで、表示のゆれ・`data-dict="<id>"` の印の文言と辞書の違い・期限切れの固定値を見る。exit 2（`docs/dictionary/` が無い・HTML を渡していない）は「確かめていない」と報告し、合格にしない。印が 0 件のときも値の照合は効いていないので、その件数を報告に書く。

プロダクト UI を渡されたら、構造・骨格・状態の 3 行は `audit_screen.py` を画面ごとに流して埋める（blueprint が無い成果物には、この 3 行は「欠落（blueprint が無い）」と報告する。黙って飛ばさない）。入力は画面の yaml（`ux/infoarch/blueprint/screens/<画面 id>.yaml`）・描いた HTML・`--repo`（描画の環境を固定する `ux/design/render-environment.json`）。描画に使える Playwright が無ければ、確かめていないと報告する（合格にしない）。

### 3. 実行順序 — 決定論が緑になるまで非決定論へ進まない

`own-website-audit` のゲート原則をルーター全体に適用する:

```
決定論（実測・機械検査） → 失格が残る間は直して再実測 → 非決定論（独立レビュアー・自己点検） → 委譲（audit）
```

理由: 表示が壊れたページを人（AI）が評価すると、出てくるのは表示不良の指摘だけで、
本来見たかった評価が汚染される。非決定論の検査は高い（レビュアー 1 名で数万トークン）。

コピーや構造を直したら、必ず決定論からやり直す。

**独立レビュアー（`own-website-audit` のマーケ採点など）は、次のゲートを通ってからだけ起動する。**

```bash
python3 <own-web-build>/scripts/reviewer_gate.py --route entry --report <実測の report.json> --ledger <ledger.jsonl>
```

`/own-web-build/scripts/reviewer_gate.py` は exit 0 のときだけ起動を許す。exit 3（止める）は、実測の結果が無い・
読めない／実行が失敗した／プロファイルが無い・知らない／測った件数が 0／失格が残っている、のどれか。止めたら
レビュアーを起動せず、報告の「スキップした検査」に理由（`reason`）を書く。`own-website-audit` を直接呼ぶ道（`--route direct`）でも
同じゲートが効き、どちらの道の起動も ledger に残る。

### 4. 報告の契約 — 沈黙させない

最終報告には必ず5区分を書く:

1. **実行した検査**とその結果（失格 / 警告 / スコア）
2. **スキップした検査**と理由（対象外 / 前段の失格で未到達 / ユーザー指示）
3. **欠落**（カバレッジ表の空欄に該当し、そもそも担当 skill が無い観点）
4. **未カバー**（担当はあっても実行可能な検査が無い規則・媒体。規則idと理由を記録し、合格に数えない）

5. **screened**（保存済みの確率判定を読んだ入力。DSのdoc/n-a意味判定は高scoreも補助指摘として表示する。実ラベルがあればholdoutのrecall等を併記し、なければ精度未測定・意味未保証。違反が無い証明やcleanと表現しない）

「実行しなかったものは書かない」を許すと、このルーターの存在意義が消える。

## カバレッジ表の保守

- 新しい検査 skill を導入・作成したら、この表に行か列を足す。
  表に載っていない skill はルーターから呼ばれず、再び沈黙に戻る。
- 空欄を埋めた（欠落を解消した）ときは、その skill 名で空欄を置き換える。
- 表の変更はこのファイルの編集で完結する（`own-skill-commonize` の
  symlink 規約に従い、どの別名から編集しても正典が更新される）。

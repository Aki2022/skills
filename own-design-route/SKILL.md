# Design Check Routing

デザイン検査の**ルーター**。検査そのものは持たない。持つのは 3 つだけ:
**対象の判定・カバレッジ表・実行順序**。

## なぜルーターが要るか

導入済み skill は 59 個あり、デザイン検査に関わるものだけで 9 個ある。
個別名を覚えるのは現実的でなく、文脈発火（description の文字列マッチ）は
発火しなかった skill が**沈黙する** — 呼ばれなかったことは誰にも見えない。

このルーターは逆の契約を結ぶ: **実行しなかった検査を、理由つきで必ず報告する。**
漏れをゼロにはできないが、漏れを**見える**ようにはできる。

## 手順

### 1. 対象を判定する

| 対象          | 判定の手がかり                                      |
| ------------- | --------------------------------------------------- |
| LP            | 広告流入前提・CV（ボタン/フォーム）がある単一ページ |
| プロダクト UI | ログイン後の画面・ダッシュボード・操作が主目的      |
| 資料          | スライド・PDF・レポート・HTML 文書                  |

迷ったら聞かずに「LP として扱う」と宣言して進める（検査が最も厚いため）。

### 2. 前提とカバレッジ表

web対象は git toplevel の `design/` を確認し、`own-design-author` のL0を実行する。
不在・失格なら生成や非決定論レビューへ進まず、定義の整備へ戻す。L0/L1は確認不要、
L2の描画検査は人間に実施可否を確認する。対象0件は失格で、準拠合格にしない。
pptxは従属WS完了までdesign/を読まないため、その制約を報告する。

**この表がこの skill の本体。** 空欄は「担当が存在しない」ことの明示であり、
検査を実行できない観点は報告にもそのまま**欠落**として書く。

| 観点                             | LP                                      | プロダクト UI                                                        | 資料                                                |
| -------------------------------- | --------------------------------------- | -------------------------------------------------------------------- | --------------------------------------------------- |
| 審美・レイアウト実測（決定論）   | `own-website-audit` の `measure_lp.mjs` | 同スクリプト流用可。ただし `fold-cta` 等 LP 前提の検査は解釈を添える | HTML資料はL0/L1/L2。pptxは `own-pptx-build` の既存決定論検査（design/連携は未カバー） |
| マーケ定性（独立レビュアー採点） | `own-website-audit` の rubric           | **欠落**                                                             | **欠落**                                            |
| 広告審査・法務・SEO・計測        | `own-website-audit`                     | `own-website-audit`（該当節のみ）                                    | 対象外                                              |
| UI ガイドライン準拠              | `web-design-guidelines`                 | `web-design-guidelines`                                              | 対象外                                              |
| アクセシビリティ修正             | `fixing-accessibility`                  | `fixing-accessibility`                                               | **欠落**（validator の自己点検のみ）                |
| 表示性能（Core Web Vitals）      | `web-perf`                              | `web-perf`                                                           | 対象外                                              |
| AI 生成様式の検出                | `baseline-ui`                           | `baseline-ui`                                                        | **欠落**                                            |
| ブランド一貫性                   | `design/` のL0と解決済みマニフェストによるL1/L2 | 同左 | HTML資料は同左、pptxのdesign/準拠は未カバー                                                |

補足:

- `own-website-audit` は LP の「審美実測 + マーケ定性 + ゲート」を 1 つで持つ。
  LP のときは個別に並べず、まず `own-website-audit` を呼ぶ。
- 重複 skill の検出は `own-skill-commonize` の `skill_lint.sh`（S7）が担う。
  `source-command-*` の対応先は現在の正典には存在しない（2026-10-12 確認）。
  ルーターは常に通常名（`baseline-ui` 等）を使う。
- 対象外のデザイン系 skill: `dataviz`（チャートの配色・作成指針で、検査ではない）と
  `artifact-design`（Claude Artifacts の作成指針）は、どちらもこの repo の正典に実体が無く
  アプリ側で提供される。検査のカバレッジ表には載せない。

### 3. 実行順序 — 決定論が緑になるまで非決定論へ進まない

`own-website-audit` のゲート原則をルーター全体に適用する:

```
決定論（実測・機械検査） → 失格が残る間は直して再実測 → 非決定論（独立レビュアー・自己点検） → 委譲（audit）
```

理由: 表示が壊れたページを人（AI）が評価すると、出てくるのは表示不良の指摘だけで、
本来見たかった評価が汚染される。非決定論の検査は高い（レビュアー 1 名で数万トークン）。

コピーや構造を直したら、必ず決定論からやり直す。

### 4. 報告の契約 — 沈黙させない

最終報告には必ず5区分を書く:

1. **実行した検査**とその結果（失格 / 警告 / スコア）
2. **スキップした検査**と理由（対象外 / 前段の失格で未到達 / ユーザー指示）
3. **欠落**（カバレッジ表の空欄に該当し、そもそも担当 skill が無い観点）
4. **未カバー**（担当はあっても実行可能な検査が無い規則・媒体。規則idと理由を記録し、合格に数えない）

5. **screened**（保存済みの確率判定で閾値未満だった入力。holdoutのrecallと陽性件数を併記し、違反が無い証明やcleanと表現しない）

「実行しなかったものは書かない」を許すと、このルーターの存在意義が消える。

## カバレッジ表の保守

- 新しい検査 skill を導入・作成したら、この表に行か列を足す。
  表に載っていない skill はルーターから呼ばれず、再び沈黙に戻る。
- 空欄を埋めた（欠落を解消した）ときは、その skill 名で空欄を置き換える。
- 表の変更はこのファイルの編集で完結する（`own-skill-commonize` の
  symlink 規約に従い、どの別名から編集しても正典が更新される）。
